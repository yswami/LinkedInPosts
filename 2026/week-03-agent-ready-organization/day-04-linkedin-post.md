Day 4/5 — The agent was ready. The organization was not.

Yesterday, we drew an autonomy envelope around a fictional invoice exception.

The agent could gather evidence, analyse the mismatch, recommend an action, and execute only after approval.

So far, so good.

Then I tried a harder scenario.

It is Friday. 4:50 PM.

The agent spots a 6.2% mismatch. It shows the purchase order, the invoice, the 48-hour supply risk, and its uncertainty. Its recommendation is reasonable:

Hold payment. Request a documented supply-continuity override.

But the decision owner is offline.

The evidence source has not refreshed.

The person viewing the recommendation cannot release or hold payment.

And the organization has no clear record of how this exception should improve the next one.

The agent did not fail.

The operating system around the agent did.

This is the distinction I think organizations need to make much more often:

**Model capability:** Can the agent recognize, explain, and recommend?

**Operating readiness:** Can people and systems receive, decide, act, reverse, and learn from that recommendation when it matters?

Before a bounded pilot, I would test five signals:

• A named decision owner, backup, and authority limit
• Usable evidence: sources, freshness, and uncertainty visible
• A real ability to intervene—not just a nominal human review
• Controlled execution, retained record, and a recovery path
• A learning loop for outcomes, overrides, and misses

None of these are solved by a better prompt or a higher benchmark score.

They are organizational capabilities.
